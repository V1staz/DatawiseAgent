\begin{frame}{Part I Analysis：InfiAgentBench 更像答案口径问题}
\begin{columns}[T]
\begin{column}{0.49\textwidth}
\begin{block}{常见失败}
\begin{itemize}
  \item 最终答案格式、小数位、引号、dict/list 格式错误；
  \item 预处理顺序、子集口径、缺失值处理错误；
  \item 相关性、显著性、正态性、异常值判断错误；
  \item 特征工程公式理解错误；
  \item reformat 从长日志中漏抽、错抽。
\end{itemize}
\end{block}
\end{column}
\begin{column}{0.48\textwidth}
\begin{alertblock}{关键判断}
很多题不是“代码完全不会写”，而是：
\begin{itemize}
  \item 题目约束没有提前固定；
  \item 统计语义没有过程校验；
  \item 最终答案通道不稳定。
\end{itemize}
\end{alertblock}
\end{column}
\end{columns}
\takeaway{InfiAgentBench 需要 answer-aware harness：盯答案名、口径、统计方法和最终格式。}
\end{frame}

\begin{frame}{Part I Scheme：InfiAgentBench answer-aware harness}
\footnotesize
\begin{tabularx}{\textwidth}{p{0.20\textwidth} X p{0.27\textwidth}}
\toprule
模块 & 作用 & 对应错误 \\
\midrule
DataCard & 固定 CSV 结构，记录列名、dtype、缺失值、范围、类别样例。 & 列选择、缺失值、类型误判 \\
Contract & 抽取 answer name、列、过滤条件、操作、小数位、输出容器。 & 口径、格式、额外清洗 \\
Skill checklist & 针对 correlation、outlier、ML、format 等题型给检查清单。 & 统计方法、ML 协议 \\
Verifier & 检查列、样本数、p-value、abs(r)、split、final block。 & 代码能跑但语义错 \\
Final Block & 机器可读答案块，再确定性转 \code{@answer[value]}。 & reformat 漏抽、占位符 \\
\bottomrule
\end{tabularx}
\takeaway{它把原本散在 notebook 长日志里的关键信息拆成结构化产物，方便检查和复用。}
\end{frame}

\begin{frame}{Part I Scheme：DataModeling 更需要 protocol-aware harness}
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{alertblock}{当前诊断}
DataModeling 的突出问题不是单个统计答案，而是评估闭环：
\begin{itemize}
  \item submission / performance 文件没生成；
  \item 输出或评估格式不匹配；
  \item metric 类型错配；
  \item jaccard 文本指标收到数值列。
\end{itemize}
\end{alertblock}
\end{column}
\begin{column}{0.49\textwidth}
\begin{block}{设计方向}
\begin{itemize}
  \item Submission checker：检查文件、列、行数；
  \item Metric checker：检查 metric 类型和输入列类型；
  \item Performance parser：统一读取结果；
  \item Evaluation adapter：避免协议错配。
\end{itemize}
\end{block}
\end{column}
\end{columns}
\takeaway{DataModeling 这一段要保守讲：目前是 protocol failure 诊断和方案设计，还不是系统消融结果。}
\end{frame}

\begin{frame}{Part I Result and Thinking}
\begin{columns}[T]
\begin{column}{0.49\textwidth}
\begin{block}{InfiAgentBench 已有证据}
\begin{itemize}
  \item weak small set 中 \code{harness_light} 明显优于 baseline；
  \item task 733 的 final block/code cell 混淆问题已修复；
  \item light harness 更有性价比。
\end{itemize}
\end{block}
\end{column}
\begin{column}{0.49\textwidth}
\begin{block}{DataModeling 当前思考}
\begin{itemize}
  \item 强模型用时更短，说明少走弯路很重要；
  \item 协议正确性可能比单纯模型能力更突出；
  \item 后续需要 failure taxonomy 和 protocol harness 实验。
\end{itemize}
\end{block}
\end{column}
\end{columns}
\takeaway{任务适配告诉我们：InfiAgentBench 要做答案口径和格式收束，DataModeling 要做 submission / metric / evaluation 闭环。}
\end{frame}

\parttitle{Part II}{Structured Time-for-Performance}{多花时间不是多问几轮，而是把时间变成可验证过程}

\begin{frame}{Part II Baseline：原作现象与复现后的问题}
\begin{columns}[T]
\begin{column}{0.49\textwidth}
\begin{block}{原作里有用的现象}
弱模型可以靠 notebook-style 长交互补一部分能力：
\begin{itemize}
  \item planning；
  \item code execution；
  \item debugging；
  \item repair 后继续推进。
\end{itemize}
\end{block}
\end{column}
\begin{column}{0.49\textwidth}
\begin{alertblock}{复现后看到的问题}
\begin{itemize}
  \item 长交互不一定更好；
  \item full harness 在 hard split 上可能退化；
  \item 多分支搜索可能选错；
  \item verifier 可能过度阻断；
  \item final block 混进 code cell 会卡住 debug loop。
\end{itemize}
\end{alertblock}
\end{column}
\end{columns}
\takeaway{“时间换性能”不能理解成无脑多跑几轮，关键是多出来的时间是否有明确检查目标。}
\end{frame}

\begin{frame}{Part II Case：task 733 卡死在哪里}
\begin{columns}[T]
\begin{column}{0.47\textwidth}
\begin{alertblock}{原问题}
FinalAnswerBlock 的 JSON 被写进 Python code cell。
\begin{itemize}
  \item JSON 里的 \code{false/null} 进入 Python；
  \item 触发 \code{NameError}；
  \item debug loop 反复修，整题卡住。
\end{itemize}
\end{alertblock}
\end{column}
\begin{column}{0.50\textwidth}
\begin{block}{修复后}
\begin{itemize}
  \item final block 只进 markdown / metadata / reformat 输入；
  \item code-cell guard 检查 \code{true/false/null}；
  \item 加 request timeout 和 continue-on-error。
\end{itemize}
\vspace{0.3em}
\smallnote{复跑：\code{harness_light} success，\code{harness_full} success。}
\end{block}
\end{column}
\end{columns}
\takeaway{这类问题不是模型能力问题，是答案通道和执行通道混在了一起。}
\end{frame}

\begin{frame}{Part II Thinking：时间要花对地方}
\begin{columns}[T]
\begin{column}{0.31\textwidth}
\begin{block}{light-first}
默认只加最关键的结构化约束和 finalizer，让大多数题先稳定完成。
\end{block}
\end{column}
\begin{column}{0.31\textwidth}
\begin{block}{targeted retry}
只有 verifier fail 或高风险题，才追加修复、搜索或升级模型。
\end{block}
\end{column}
\begin{column}{0.31\textwidth}
\begin{block}{hard-aware}
hard 题不能只加分支数量，还要能做分支选择和语义复算。
\end{block}
\end{column}
\end{columns}
\takeaway{原作的长交互机制可以继续推进，但要从“交互轮数”变成“可验证的执行预算”。}
\end{frame}

\begin{frame}{Part III Scheme A：小模型使用规则}
\footnotesize
\begin{tabularx}{\textwidth}{p{0.20\textwidth} p{0.22\textwidth} X}
\toprule
阶段 & 默认资源 & 使用原则 \\
\midrule
Schema / Contract / Verifier / Finalizer & deterministic 优先 & 能程序化就不问模型；同一 CSV 的 schema 和列映射复用。 \\

\bottomrule
\end{tabularx}

\begin{frame}{融合后的四个发现}
\begin{columns}[T]
\begin{column}{0.48\textwidth}
\begin{block}{1. 失败模式不是统一的}
InfiAgentBench 主要错在答案口径、统计协议和最终格式；DataModeling 主要错在 submission、metric 和 evaluation 协议。
\end{block}
\begin{block}{2. 长交互有效，但必须结构化}
light harness 说明结构化步骤能提升 small set；full harness 说明无控制增加检查和分支会带来高 runtime，甚至 hard 退化。
\end{block}
\end{column}
\begin{column}{0.48\textwidth}
\begin{block}{3. 强模型和小模型都要看场景}
强模型可能少走弯路；小模型只适合简单、明确、短上下文子任务。
\end{block}
\begin{block}{4. 最终系统应该做风险调度}
low risk 用 deterministic / small instruct，medium risk 用 small model + verifier，high risk 用 32B thinking + targeted fallback。
\end{block}
\end{column}
\end{columns}
\takeaway{这把三个人的工作收束成一个系统问题：任务、过程和预算一起调度。}
\end{frame}
